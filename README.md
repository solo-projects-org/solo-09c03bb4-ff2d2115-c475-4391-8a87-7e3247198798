# 回收申报出库量换算底表与签收对账 API

回收申报核对出库量时,同一商品可能按 **箱 / 提 / 件** 等不同单位记账。本服务用
**FastAPI + SQLite** 提供包装换算底表、出库批次折算与**签收单对账**能力:

- 两仓(A / B)各自**整表更换**包装换算关系,按商品填**正整数比**(`1 源单位 = ratio 目标单位`);
- 换表提交时,与**另一仓提交时的现行关系**合并校验:同一商品的**任意换算路径**必须得出
  相同比例;有矛盾则指出**能证实矛盾的关系及来源仓**,**保留原表**(409,不写入);
- 出库批次按行(行号 / 商品 / 数量 / 单位)入库,按批查询时**逐行精确折成件**,
  换算不到的行标为 **待补**;
- 一次查询使用**同一份已提交**的换算关系(单读事务快照);换表成功后,
  **已入库批次也按新关系出数**(折算在查询时按当前生效底表现算);
- **签收对账**:每批每种商品只开一单,开单时提交至多 12 条签收行(行号 / 件数 /
  候选出库行号);冻结所选商品各出库行折件数与两仓底表版号,有待补出库行则退回。
  返回**最少要暂缓入账**的签收行,以及其余行将全部件数拆分归属到候选出库行的一份
  完整方案(精确分数,各出库行不超冻结件数);核对员可把签收行标为已核实,之后的
  建议必须保留这些行;若已核实行加本次核实行无法同时归属,则整次退回本次核实并
  按原状态出对账结果;同一行重复核实只记一次。

## 快速启动

### Docker Compose(推荐)

```bash
docker compose up --build
```

服务监听 `http://localhost:8000`,Swagger UI 在 `http://localhost:8000/docs`。
SQLite 数据落在命名卷 `app-data`(`/data/app.db`),重启不丢。

### 本地开发

```bash
python3 -m venv .venv
.venv/bin/pip install -r requirements.txt -r requirements-dev.txt
.venv/bin/uvicorn app.main:app --reload          # http://127.0.0.1:8000/docs
.venv/bin/python -m pytest -q                    # 运行自测
```

数据库路径可用环境变量 `APP_DB_PATH` 覆盖(默认 `data/app.db`)。

## Swagger 演示:换表前后的结果

打开 `http://localhost:8000/docs`,按顺序执行(每个接口都预置了示例报文,可直接 Try it out):

1. **`GET /warehouses/A/conversion-table`** — 确认换表前底表(A 仓 v1,如上表)。
2. **`POST /batches`** — 提交出库批次(示例报文已预置):
   `OUT-20261122-001`,含 P001 5箱 / P001 3提 / P003 2箱 / P002 7箱 / P001 10件 / P004 3提 / P999 1箱。
3. **`GET /batches/OUT-20261122-001/pieces`** — **换表前**结果:
   行1 `360`、行2 `18`、行3 `20`、行5 `10` 已换算;行4/6/7 **待补**(无换算关系)。
4. **冲突换表:`POST /warehouses/B/conversion-table`** 提交 `P001 1提=5件`
   → **409**,响应指出能证实矛盾的关系(`P001 1提=6件`,来源仓 **A**)及校验所依据的
   两仓版本;再查步骤 1 可见 **A 仓仍是 v1,原表保留**。
5. **一致换表:`POST /warehouses/B/conversion-table`** 提交
   `P001 1箱=72件`(与 A 仓 12×6=72 一致)、`P002 1箱=24件`、`P004 1件=5提` → **200**,B 仓 v1。
6. **A 仓整表更换:`POST /warehouses/A/conversion-table`** 提交
   `P001 1箱=12提`、`P001 1提=6件`(与 B 仓 72 保持一致,否则 409)、`P003 1箱=20件` → **200**,A 仓 v2。
7. **再次 `GET /batches/OUT-20261122-001/pieces`** — **换表后**,同一已入库批次按新关系出数:
   行3 `20 → 40`(P003 新比例)、行4 `待补 → 168`(P002 有了关系)、
   行6 `待补 → 3/5`(1件=5提,精确分数)、行7 仍待补;`relation_versions` 变为 `{A:2, B:1}`。
8. **`GET /conversion-table/effective`** — 查看两仓合并后的现行关系及各自来源仓。

## Swagger 演示:签收对账

先完成上面步骤 1–2(建批次 `OUT-20261122-001`),然后:

9. **`POST /batches/OUT-20261122-001/reconciliations`**(示例报文已预置)——以
   `product=P001` 开单,提交 4 条签收行。P001 出库行折件数冻结为:
   行1 `360`、行2 `18`、行5 `10`(换表后数据不同则以开单时为准),响应
   `relation_versions` 冻结开单时的 `{A, B}` 版号。示例中签收行 1/2/3 分别正好
   占满 360/18/10,行 4(`5` 件,只能去行 1)会被建议**暂缓**,其余行给出完整归属。
10. **`POST /batches/OUT-20261122-001/reconciliations/P001/verify`** 提交
    `{"line_nos":[4]}` —— 核实该行;响应 `newly_verified=[4]`,之后的建议
    **必须保留**行 4(其他行改被暂缓,但已核实行不会再进暂缓名单)。
11. **再次提交同一行** —— `newly_verified=[]`、`already_verified=[4]`,
    `revision` 不增加(重复核实只记一次)。
12. **提交 `{"line_nos":[1,2,3]}`** —— 与已核实的行 4 争抢行 1 容量,无法同时归属,
    **409** 且 `reconciliation` 为**原状态**(行 4 仍是唯一已核实、建议不变),
    本次核实整体退回。
13. **`GET /batches/OUT-20261122-001/reconciliations/P001`** —— 随时查看冻结数据
    与当前建议;换表后再查,冻结的出库件数与版号**不会改变**。

## API 一览

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/warehouses/{A\|B}/conversion-table` | 某仓当前生效底表(含版本号) |
| POST | `/warehouses/{A\|B}/conversion-table` | 整表更换;矛盾返回 409 + 证实关系及来源仓 |
| GET | `/conversion-table/effective` | 两仓合并后的现行关系(折算实际使用的底表) |
| POST | `/batches` | 接收出库批次(行号/商品/数量/单位) |
| GET | `/batches` / `/batches/{batch_no}` | 批次列表 / 原始行 |
| GET | `/batches/{batch_no}/pieces` | 逐行折成件的精确数量,待补行给原因 |
| POST | `/batches/{batch_no}/reconciliations` | 开对账单(每批每种商品一单),冻结出库件数与底表版号,返回最少暂缓建议 |
| GET | `/batches/{batch_no}/reconciliations/{product}` | 查看冻结数据与当前对账建议 |
| POST | `/batches/{batch_no}/reconciliations/{product}/verify` | 核实签收行;冲突整次退回并返回原状态结果 |

## 设计要点

- **一致性模型**(`app/converter.py`):同一商品的单位为节点,`1 from = ratio to` 为带权边
  (反向边权 1/ratio)。合并两仓关系后,同一对单位间若存在多条路径,各路径比例必须一致。
  校验时先入图另一仓现行关系,再逐条加入提交关系;不一致即记录**提交关系 + 现行关系链**
  (每条带来源仓)作为矛盾证明,矛盾关系不入图,继续检查其余关系,一次返回全部矛盾。
- **并发换表**(`app/db.py` 的 `write_tx`):换表全程在 `BEGIN IMMEDIATE` 写事务内
  (读另一仓现行关系 → 校验 → 写入),SQLite 写锁使并发换表串行化,后到者读到的一定是
  先到者**已提交**的现行关系,即"按提交时另一仓的现行关系核准";校验失败抛异常即回滚,
  原表保留(旧版本同时归档为 `superseded`,可审计)。
- **查询快照**(`read_tx`):一次 `/pieces` 查询的批次行与两仓底表在同一个读事务
  (WAL 快照)内读取,响应附 `relation_versions` 标明所用版本。
- **精确数量**:数量按十进制字符串存储,折算用 `fractions.Fraction` 运算,结果以
  整数或分数字符串返回(如 `360`、`3/5`),无浮点误差。
- **待补**:商品无任何换算关系,或该单位与「件」之间无换算路径的行,标 `待补` 并给原因;
  单位本来就是「件」的行无需任何关系即可出数。
- **对账模型**(`app/reconcile.py`):视为带需求与容量的二部分数流——源→签收行(容量=件数)、
  签收行→候选出库行(容量无限)、出库行→汇(容量=冻结件数);可行当且仅当最大流等于签收
  件数之和。所有容量用 `Fraction`,分数容量 Dinic 无浮点误差。
  目标是**先最少暂缓行数,再最少暂缓件数合计**,并列时保留行号更小的行。签收行至多 12 条,
  直接枚举暂缓子集(≤2^12)逐一判定,得到精确全局最优;12 行满载实测约 2 ms/次。
- **开单冻结**(`app/db.py` 的 `write_tx`):开单在 `BEGIN IMMEDIATE` 内读取该商品出库行、
  两仓现行关系与版号并落库;出库行折件数、候选关系、底表版号均冻结。之后换表或改批次都
  不影响已开的对账单(核实时同样以冻结数据为准)。该商品的任何出库行若仍**待补**,开单
  409 退回并列出待补行。每批每种商品受 `UNIQUE (batch_id, product)` 约束,只开一单。
- **核实与并发**:核实走 `BEGIN IMMEDIATE` 写事务,"读已核实集合 + 本次集合 → 判定合并后
  是否可行 → 写入"整体串行化。已核实行一律参与可行性判定,不可暂缓;若与本次核实行无法
  同时归属,不写任何变更(抛 409),409 响应体直接附带**原状态**的完整对账结果。同一行
  重复核实只记为一次(已核实行保留原 `verified_at`,不增加 `revision`);并发重复核实由
  写锁串行化,后到者观察到已核实并计入 `already_verified`。

## 自测与验证结果

- `pytest`:**54 项全部通过**(`tests/test_converter.py` 9、`tests/test_api.py` 13、
  `tests/test_reconcile.py` 14、`tests/test_reconciliation_api.py` 18),覆盖:
  - 直接矛盾与传递矛盾(箱→提→件 路径 72 vs 提交 100)的识别与证明链、来源仓标注;
  - 冲突换表后 A/B 两仓原表均保留;
  - **并发冲突换表**:两线程同时提交互相矛盾的 P009 底表,断言**恰一成功(200)一失败(409)**,
    失败方看到的矛盾证明来自胜方仓库,最终生效关系与胜方一致;
  - 换表后已入库批次按新关系出数、空表更换、精确分数(`3/5`)、十进制数量(`0.5箱 → 36件`)、
    待补标注、批次号重复 409、非法输入 422 等;
  - 对账纯逻辑:最少暂缓(含"能装下总量但连通性/候选受限仍须暂缓")、精确分数容量、
    拆分归属守恒、已核实必须保留、已核实不可行报错;
  - **随机化对照**:300 个随机小实例上,算法结果与穷举全部暂缓子集的最优解逐一相同,
    并校验归属守恒、不超冻结容量、候选合法;
  - 对账 API:12 行上限、每批每种商品一单(并发开单 201/409 恰一)、待补出库行拒开、
    非法候选 422、开单后换表不影响冻结值、核实后必须保留、核实冲突 409 且返回原状态、
    重复核实只记一次(并发重复核实 `revision` 只加一)、并发核实争抢容量恰一成功一冲突。
- 本地以 Docker 同款命令(`uvicorn app.main:app`)实跑,按上面"Swagger 演示"1–13 步逐步用
  HTTP 请求验证,换表前后结果与预期一致(见上表演示数字),`/docs` 与 `/openapi.json` 正常。

## 未完成事项 / 已知限制

- 本交付环境没有 Docker,`Dockerfile` / `docker-compose.yml` 未实际构建运行,仅做静态核对;
  应用进程以镜像内同一启动命令本地验证通过。请在有 Docker 的机器上 `docker compose up --build` 复核。
- 仓库固定为 A、B 两仓(需求为两仓);新增仓库需扩展 `CHECK` 约束与 `Warehouse` 字面量。
- 矛盾报告按"每条提交关系 + 一条现行证明路径"给出,未枚举全部等价证明路径。
- 无认证鉴权;多实例水平扩展需换用集中式数据库(SQLite 单写者)。
- 旧版本底表已归档(`superseded`)但暂未提供历史版本查询接口。
- 对账单暂不支持撤销/重开或修改签收行(开单后冻结);核实无操作人留痕,仅记录时间与次数。
- 开单要求该商品**所有**出库行都可折算;若只想对部分出库行开单,当前需先补全底表。
